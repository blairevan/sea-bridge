# Codex 消息一直排队：一次非侵入式恢复实验

> 状态：Sea-Bridge v0.7.0 已部署；本文是发推素材草稿，尚未发布。原生导航实验通过，macOS 外部深链完整路径尚未实机验收。不要将其宣传为通用修复或深链端到端已经验收。

## 可直接整理成推文的正文

我遇到一个 Codex 使用问题：从 Telegram / 网页发来的消息已经成功入队，却迟迟不执行；打开对应 Codex 会话后才继续。

最重要的区分是：**入队成功，不等于会话已经加载，更不等于任务已经开始。**

为避免猜测，我创建了临时会话，通过归档再恢复构造“未加载”状态，然后只投递一条测试消息。等待 20 秒后，原生状态仍为 `notLoaded`，队列计数为 1。

接着通过 Codex 自带的导航工具打开该会话。20 秒后的检查显示，原有消息已经执行完成，队列计数变为 0。整个过程没有重复发送提示词，也没有替换 Codex 后端。

基于这次实验，Sea-Bridge 增加了一个手动入口：“在 Mac 上打开会话”。从手机点击并确认后，由运行 Sea-Bridge 的 Mac 请求打开对应 Codex 会话。

技术上使用当前安装包支持的 `codex://threads/<UUID>` 链接，经 macOS Launch Services 打开。输入限定为已知未归档会话的 UUID；服务端认证、Origin、CSRF 校验继续生效，并限制并发和短时间重复点击。

它是一个非侵入式恢复入口：不改 Desktop 配置、不切换后端、不注入补丁、不接管队列调度。可能切换 Mac 窗口，因此只由用户手动触发。

需要诚实说明：已验证的是“原生导航打开会话后，已有队列恢复执行”。Sea-Bridge 经 macOS 外部深链打开的端到端路径仍待验收；一次构造实验也不能证明所有偶发卡住都是同一个原因。

所以页面提示是“已请求 Mac 打开会话”，而不是“恢复成功”。只有真实执行结果，才能证明消息开始处理。

## 实现链路

```text
手机：点击“在 Mac 上打开会话”并确认
  → 已配对的 Sea-Bridge POST 请求
  → 认证 / Origin / CSRF / 会话校验 / 并发限制
  → Mac：/usr/bin/open codex://threads/<UUID>
  → Desktop 按自己的逻辑加载会话
  → 持续观察原生队列与执行记录
```

- 成功回执：`open_requested`，只确认打开命令成功返回。
- 不新增提示词，不调用 `turn/start`，不自动重试打开请求。
- 未支持平台隐藏入口；DSH 会话不提供此操作。
- 保留首轮所有权检查，避免 Sea-Bridge 自有后端仍执行时打开会话。
- 打开失败或响应丢失不等于没有产生界面动作，先观察再手动决定。

# Sea-Bridge Web 控制台设计

- 日期：2026-10-02
- 状态：用户已确认（2026-10-02），已进入实施计划阶段
- 范围：状态监控、问题排查、新建会话、发送消息、本机与 Tailscale 访问

## 1. 目标与布局

提供统一的中文管理控制台，复用现有 Codex Desktop、dsh 和 Telegram 桥接能力。
桌面采用侧边导航、会话列表、会话详情三栏布局；手机采用列表和详情分屏，输入框固定底部，新建会话为全屏表单。

```text
┌─────────────────────────────────────────────────────────────┐
│ Sea-Bridge       Codex ●   dsh ●   Telegram ●       设置 ⚙ │
├──────────┬─────────────────┬────────────────────────────────┤
│ 概览     │ 会话            │ 会话名称              来源标识 │
│ 会话     │ [+ 新建会话]    │ 项目 / 状态 / 更新时间         │
│ 操作记录 │ [搜索……]        ├────────────────────────────────┤
│ 设置     │ 来源：[全部 ▾]  │ 用户消息                       │
│          │                 │ 助手最终回复                   │
│          │ 会话列表        │ 提交状态 / 错误详情            │
│          │                 ├────────────────────────────────┤
│          │                 │ [输入消息……]          [发送]   │
└──────────┴─────────────────┴────────────────────────────────┘
```

概览展示来源连接状态、最近会话、最近桥接记录。会话支持来源筛选、标题搜索、历史查看、发送与新建。新建表单包含来源、项目、模型和首条消息。操作记录支持按执行来源、会话、状态和时间筛选，用于排查 Web/Telegram 桥接与来源调用结果；它不冒充完整聊天记录，完整可读内容只在会话详情中按来源实际能力展示。设置包含 Web 控制台全局脱敏开关、脱敏规则说明、设备管理；首版不编辑密钥或其它运行配置。

术语固定为两层：`executionSource` 表示真实执行来源（`codex`、`dsh`），`transport` 表示入口/通知通道（`web`、`telegram`）。Telegram 不是第三种会话来源，筛选和日志不得把 transport 与 executionSource 混为一谈。

## 2. 方案与取舍

选定管理控制台布局：监控和会话操作有独立入口，适合多来源桥接。聊天工作台更适合持续对话，但问题排查入口较弱；单页仪表盘初期简单，但记录与会话增长后拥挤。

由现有 Bun 进程提供静态网页及同源 API，使用现有 TypeScript、Bun SQLite 和浏览器原生能力，不新增运行依赖。业务数据定时刷新，设置同步与设备撤销采用 SSE；SSE 只发送设置版本、会话失效等控制事件，不承载会话正文。首版不实现逐字流式回复、终端模拟器、工具调用全文、网页审批、文件上传或会话删除。

静态资源必须与现有 `bun run build` 的交付方式兼容：不能依赖运行目录恰好存在 `src/web/`。实施时选择可随构建产物稳定发布的嵌入或复制方案，并增加“仅保留 `dist` 后仍能打开控制台”的构建验收，避免开发态可用而部署态 404。

## 3. 现有代码与接入边界

- `src/main.ts` 负责服务生命周期，新增 Web 服务随主进程启动和关闭。新增 `SEA_BRIDGE_WEB_ENABLED`、`SEA_BRIDGE_WEB_PORT` 与独立 Web control socket 配置；HTTP host 固定为 loopback，不提供可改成 `0.0.0.0` 的通用 host 配置。为兼容现有部署，Web 默认关闭，实施/部署验收通过后再在目标 LaunchAgent 显式启用。Web 端口冲突、Tailscale 未就绪或 Web 专用迁移失败时应将 Web 标记为不可用并记录原因，不能拖垮现有 Telegram/dsh 主链路；共享 StateDb 本身损坏等已有致命错误仍按原生命周期处理。
- `CodexThreadStore` 提供现有未归档会话；`ThreadHistoryStore` 当前只可靠提供轮次状态和最终助手回复。现有 `rollout-parser` 只提取终态事件与最终助手文本，**没有用户消息读取能力**。若 Web 详情需要展示 Codex 历史用户消息，必须新增独立、只读、带 schema fixture 的 transcript 解析器；只接受已验证的 user/assistant message 结构，不展示工具调用全文。读取 `rollout_path` 前必须做真实路径约束、普通文件检查和大小/分页限制，防止数据库中的路径值形成任意文件读取。
- `CodexAppServerClient` 提供项目、模型及创建会话并启动首轮；`ProcessCodexQueueClient` 负责已有会话消息入队。当前 `startThreadAndTurn()` 会给首条消息硬编码 `[Telegram init]`，实现 Web 前必须将其改造成来源中立的底层接口，再由 Telegram 适配层显式添加 Telegram 标识；Web 不得发送伪 Telegram 前缀。Web 新建 Codex 会话仍沿用现有 App Server 审批处理器，所以首版需要审批的工具操作继续通过 Telegram 完成，页面只显示“等待外部审批/审批通道为 Telegram”，不伪装成 Web 已支持审批。
- `DshWebHostClient` 提供健康、项目、模型、会话、历史元数据、按轮次最终助手回复以及创建和提交接口。当前 dsh 合约**不提供既有用户消息正文，也不保证每个会话都可反查所属项目**；Web 对旧 dsh 会话只能展示有证据的数据，项目或用户正文缺失时显示未知/不可用。Web 自己提交的 dsh 用户消息可由 Web 操作存储补充显示，但不能据此声称拥有完整历史。
- 现有 Telegram 路由和持久化使用 Telegram 消息或 update ID；网页不得伪造这些 ID 或复用其去重表。
- `src/security/redact.ts` 已有部分密钥过滤；需增加统一展示策略与正文过滤。
- 当前 logger 主要输出到控制台；增加有期限、有限量的结构化日志存储，历史未存储日志不能宣称可查询。

建议新增 `src/web/`：HTTP 路由、鉴权配对、来源适配、请求记录、展示过滤、设置事件以及静态资源分别负责单一职责。新增迁移放在独立模块，避免继续扩大 `StateDb` 的职责；Web 表采用自己的迁移版本记录并以事务执行前向、幂等迁移。只调整本功能需要的共享接口，不重构无关模块。

来源适配层负责消化现有 Telegram 专用 manager 的耦合：Web 操作不得借用 `telegram_update_id`、`telegram_chat_id` 或 Telegram 默认模型状态。可复用底层 Host/App Server 客户端与校验逻辑，但 Web 的幂等状态、显式模型选择和设备审计必须落在独立 Web 状态中。

统一来源接口包含项目、模型、会话、历史、创建、发送和能力状态。每次操作明确使用 executionSource 与会话 ID；模型按单次请求传递，不临时修改 Telegram 默认模型。dsh 仍受现有读写功能开关控制。能力接口必须区分“可读、可新建、可续发、可取完整用户历史、可取最终回复”等能力，前端按能力降级，不能用一个 `available` 掩盖部分能力缺失。

Codex 会话列表与详情也采用证据优先：现有 thread 元数据没有稳定项目字段时不猜项目；只有能从已验证来源安全关联时才显示项目，否则显示“未知”。列表、搜索和历史 API 都必须有服务端上限和分页；项目/模型目录使用现有短 TTL 缓存，不随 3 秒页面刷新反复启动 App Server 进程。

顶部状态采用证据型三态/能力摘要，不把“进程存在”渲染成虚假的实时连接：Codex 至少区分 thread 数据可读、CLI/queue 可用、新建 App Server 可用；dsh 使用现有 health 与 read/write capability；Telegram 展示服务生命周期及最近成功/错误证据，没有新鲜证据时允许显示未知。状态探测失败不得触发高频子进程风暴。

## 4. 数据流与操作状态

读取：鉴权 → 来源或本地桥接记录 → 统一数据结构 → 当前全局展示策略 → 响应。
写入：鉴权及同源校验 → 输入验证 → 持久化请求认领 → 指定来源调用 → 更新结果 → 网页显示。

网页创建和发送使用浏览器 `crypto.randomUUID()` 生成的 Web 操作 ID；同一次点击及其网络重试必须复用该 ID。服务端在调用任何来源前先原子认领操作，并保存 `operationKind + executionSource + target/project + model + prompt` 的规范化摘要、设备、状态和返回标识。同 ID 同摘要返回已有结果；同 ID 不同摘要拒绝。摘要只用于幂等比较，不替代正文展示存储，也不得包含可恢复的真实密钥。dsh 上游 `requestId` 从 Web 操作 ID 派生独立命名空间；Codex `queue` 没有上游幂等键，因此一旦状态进入派发边界，服务端重启或连接丢失都只能标为结果待确认，禁止自动再次调用。创建成功而首条消息未确认时必须立即持久化已创建会话标识，避免重复创建。

显示状态区分提交中、已入队（仅表示 Codex `queue` 进程成功）、已接受（来源明确确认提交）、明确失败、结果待确认。`已入队` 不等于来源已经开始执行。执行中和已完成必须来自已验证的轮次证据；无法确定时显示未知。dsh busy/writer-held 显示暂不可发送，不自动排队。来源不可用只影响对应来源。

Web 新建 Codex 会话的首轮由 Sea-Bridge 自己启动的 App Server session 暂时持有，直到 `turn/completed` 后 unsubscribe/释放。在该所有权释放前，页面不得把后续消息通过 `codex queue` 发送到同一新建 thread，避免跨 owner 竞争；UI 显示“首轮执行中/暂不可续发”。已有 Desktop thread 仍按现有 `codex queue` 语义工作。

会话及选中详情在前台每 3 秒刷新，后台暂停，回到前台立即刷新；同一查询不并发重叠。项目/模型目录、静态能力和昂贵健康探测不参加 3 秒轮询。历史分页，保持输入草稿、阅读位置和稳定消息标识。无法读取的历史明确提示；仅有最终回复时按轮次展示，不伪造完整对话。来源稳定标识优先使用 Codex turn/item 标识或 dsh seq；Web 自身提交的消息使用 Web 操作 ID 补充展示，并与来源返回标识去重。

所有列表、历史、搜索参数和请求体都设置上限；消息长度按来源能力分别校验，不能把 dsh 的 8192 字符限制误套为所有来源的协议能力，也不能让 Codex 命令行参数无限增长。超限在派发前返回稳定验证错误。

## 5. Web 控制台全局脱敏

默认开启，作用域是 Web 控制台的展示与新增 Web 日志，不改变 Telegram 现有展示行为，也不修改上游原始会话。覆盖配置、会话标题、项目展示、消息正文、日志和错误信息；SSE 本身只发送控制事件，不发送正文。数据库保存开关和单调递增版本。所有已配对设备均可修改，更新须提交预期版本，冲突时提示刷新后操作。记录设备、时间与开关值审计，不记录敏感原文。

始终过滤已知配置密钥值、明确标注的密码、Token、Authorization/Cookie 及私钥内容。关闭脱敏也不返回这些内容。开启时额外遮盖可识别邮箱、手机号、IP 和本机路径；规则需集中实现并覆盖多行文本、嵌套对象和 URL。自动识别无法保证覆盖任意自然语言个人信息，界面用简短说明表达此边界。

展示策略不改写发给来源的任务内容，不改写上游会话历史。存储过滤与展示过滤分层：密钥类内容在写入 Web 新增正文/日志前永久过滤；邮箱、手机号、IP、本机路径等普通隐私字段只有在 Web 脱敏开启时于响应阶段遮盖，从而支持关闭脱敏后的诊断。已在存储阶段过滤的内容无法恢复。Web 自己为补齐 dsh/Codex 用户消息而保存的正文，也只能保存“已永久去密钥”的版本，并受第 7 节期限和数量限制。

每个动态响应带设置版本并设置 `Cache-Control: no-store`。开关更新后 SSE 通知全部设备；客户端收到更高版本时清空已渲染敏感数据并重新加载。客户端观察到 SSE 断线、页面从后台/冻结状态恢复或 `pageshow` 恢复时，先获取最新设置再继续展示。浏览器不将消息原文存到 localStorage、IndexedDB 或 Service Worker 缓存。

脱敏同步是展示策略同步，不是秘密撤销机制：已经返回到浏览器、正在网络途中、已看到、复制或截屏的内容无法可靠追回；因此任何真正的密钥无论开关状态都必须执行常驻过滤。规格和 UI 不宣称“关闭某设备/切换脱敏后可撤回已经下发的数据”。

操作 ID 作为机器标识保持可寻址，界面显示可遮盖；脱敏不是隐藏协议中必须使用的会话标识的访问控制机制。

## 6. 本机与 Tailscale 访问、首次配对

Bun 服务只绑定 loopback，禁止监听 `0.0.0.0` 或 Tailnet IP。远程入口使用 Tailscale Serve 将 Tailnet 内 HTTPS 反向代理到 loopback；不使用 Funnel。应用启动流程不自动启用 Tailnet HTTPS、不自动覆盖既有 Serve/Funnel 配置。部署时先读取并核对当前 Tailscale 版本、Serve 配置、HTTPS 能力和目标端口冲突，再显式配置唯一 Web 路由；环境不满足时只保留本机访问并报告“远程未就绪”。

Tailscale Serve 的网络访问控制是第一层远程边界，Sea-Bridge 配对是第二层应用边界。仅当请求的 Host 精确匹配已配置的 Serve 主机、后端连接来自 loopback 且部署检查确认该地址由 Serve 代理时，才把 Serve 注入的 `Tailscale-User-*` 头当作审计/限速辅助信息；这些头不能单独授予 Sea-Bridge 权限，也不信任客户端提供的任意 `X-Forwarded-*`。对没有用户身份头的 tagged device 仍要求配对，并落入独立远程/全局限速桶。Tailnet share/ACL/grants 的实际范围在部署验收中记录，不能把“位于 tailnet”直接等价为“允许使用控制台”。

本机及远程浏览器都需要配对。增加独立的本机控制 socket 与命令生成配对码；socket 父目录保持私有权限，远程 HTTP 不暴露该控制接口。配对码为密码学安全随机的 8 位数字、5 分钟有效、单次使用，新码使前一码失效。由于 8 位数字本身熵较低，活动配对码不以可离线穷举的普通哈希持久化到 SQLite：仅在进程内保存由进程随机密钥计算的 MAC 摘要和到期/失败计数，进程重启即失效。配对码只向本机命令调用者显示，不写日志。

配对页在认证前只提供配对表单，不暴露状态、配置、会话、日志或来源能力。配对成功后生成至少 256 bit 随机会话令牌，只把其不可逆摘要保存到数据库，并设置 HttpOnly、SameSite=Strict Cookie；远程 HTTPS Cookie 必须带 Secure，本机 HTTP 使用独立 host-only Cookie。设备会话绝对有效期 30 天，不滑动续期。设备名称由配对时可选输入提供，做长度与字符校验，不做浏览器指纹识别。

配对接口限制请求体及频率：单来源每分钟最多 5 次失败，单配对码累计 10 次失败即失效，并设置全局失败速率上限防止并发猜码；失败响应保持通用，不泄露“码是否存在/是否过期”等可用于枚举的细粒度差异。远程来源限速优先使用受信 Serve identity 的摘要，不存在 identity 时使用受控的远程桶，不能用后端看到的 `127.0.0.1` 作为所有远程用户唯一的“源 IP”逻辑。

所有写 API 校验精确 Origin 与 Host 白名单，无开放 CORS。配对成功时同时生成高熵 CSRF token：原值放入独立、host-only、SameSite=Strict、可由前端读取的 CSRF Cookie（远程 HTTPS 同样要求 Secure），数据库只保存与设备 session 绑定的摘要；写请求必须同时满足 HttpOnly 会话 Cookie、Origin/Host、CSRF Cookie 与同值 header，避免多标签页轮换 token 互相失效。CSRF token 不放 URL、不放 localStorage。配对接口本身也执行精确 Origin/Host 检查和限速。SSE 只用会话 Cookie 鉴权，不把会话或 CSRF token 放进查询参数；设备撤销/过期后服务端主动关闭连接。

HTML 与动态 API 使用 `Cache-Control: no-store`；静态指纹资源可长期缓存。页面设置严格 CSP（至少限制为 self，禁止 object、base、frame，避免 inline script）、`X-Content-Type-Options: nosniff`、禁止被 frame 嵌入，并使用文本节点/`textContent` 展示来源内容。首版按纯文本保留换行，不解析来源 HTML；若以后增加 Markdown，必须作为独立安全设计评审。

设备页显示设备名称、配对时间、最近活动与当前设备，可撤销任意设备；撤销立即使对应 session 失效并关闭其 SSE，后续 API 返回未认证。已经进入来源派发阶段的在途写操作不能假装被“撤销回滚”，仍按结果待确认/最终结果记录审计。所有配对设备具有同等控制权限，首版不引入角色系统。

## 7. 持久化、日志与错误处理

新增独立表保存 Web schema 迁移版本、设置及版本、设备会话/CSRF 摘要、Web 操作、用于补齐展示的 Web 消息快照、结构化日志与审计；活动配对码不落 SQLite。保留 Telegram 与 dsh 现有表语义，仅做增量迁移。设备会话令牌、CSRF token 均只保存高熵值的摘要；密钥不进入新增日志、正文快照或操作摘要。为结果待确认的创建操作尽早保存已知来源会话 ID。

结构化 Web 日志默认保留 7 天，最多 10000 条；Web 操作、消息快照和审计默认保留 30 天，最多各 10000 条，启动与运行时按时间和数量双重清理。分页读取，不扫描或暴露任意系统日志文件，也不宣称能补查功能上线前没有落盘的 console logger 历史。详细会话消息优先按需读取来源；只有在来源缺少用户正文、Web 幂等/状态恢复或 UI 补齐确有需要时，才保存 Web 提交正文的“永久去密钥”快照，且不因此改变发往来源的原始任务内容。

API 使用稳定错误码及中文说明，页面提供明确的加载、空列表、来源离线、部分数据不可用、等待 Telegram 审批、首轮暂不可续发和配对失效状态。未知提交结果提供刷新核查入口，不提供自动重试。拒绝直接展示未经处理的底层异常；底层异常先映射为稳定错误码，再经过常驻密钥过滤后才允许写日志。网页内容以文本或安全 DOM 渲染，禁用来源消息中的原始 HTML。

## 8. 验证与验收

自动测试覆盖：配对有效期、单次使用、进程重启失效、低熵配对码不落库、猜码限制、设备撤销、会话/CSRF 摘要、Cookie、Origin/Host 与 CSRF 限制；受信/伪造 Tailscale 头处理；来源隔离与细粒度能力降级；请求原子认领、去重与摘要冲突；Codex queue 派发后断线/重启的结果待确认；新建部分成功及已创建会话 ID 保留；Web 新建 Codex 不出现 `[Telegram init]`、首轮 owner 释放前不可续发、Telegram 新建行为保持原样；模型按单次请求隔离且不改 Telegram 默认值；dsh 旧会话缺用户正文/项目时正确降级；Codex transcript 路径逃逸与非普通文件拒绝；Web 脱敏版本冲突、两设备同步、旧响应丢弃、断线/恢复；密钥常驻过滤与正文存储规则；日志清理、分页和迁移；CSP/纯文本渲染及来源文本脚本注入防护。

仓库现有命令为 `bun test`、`bun run typecheck` 和 `bun run build`。当前没有 lint/format 脚本，不擅自安装工具；实施前重新核对可用检查，运行相关测试与现有全套测试，分别报告结果。构建验收除 `bun run build` 外，还必须从不依赖源码目录的构建产物启动一次 Web 服务并请求 HTML/JS/CSS/API，证明静态资源没有隐藏的 `src/` 路径依赖。

实机验收覆盖本机、手机和第二台 Tailnet 电脑：确认 Web 后端只监听 loopback；核对 Tailscale Serve 为 Tailnet 内 HTTPS 且没有 Funnel 暴露，记录实际 Serve URL、Tailnet ACL/grants 可达范围和 identity header 行为；首次配对、错误码爆破限制、刷新保留登录、设备撤销；创建 Codex/dsh 会话并发送首轮、Codex 首轮 owner 释放后的指定会话续发、需要审批时 Telegram 审批链路、真实最终回复与状态；dsh busy/writer-held；断线与来源重启；双设备脱敏同步，以及 Telegram 原有链路回归。本次设计阶段未执行上述运行验收，不把源码存在视作运行能力已确认。

部署脚本或人工步骤在修改 Tailscale Serve 前必须先检查现有配置并避免覆盖其它服务；Sea-Bridge 进程本身不负责自动执行不可逆/全局性的 Tailnet 配置变更。

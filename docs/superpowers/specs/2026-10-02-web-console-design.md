# Sea-Bridge Web 控制台设计

- 日期：2026-10-02
- 状态：交互设计已确认，书面规格待用户审核
- 范围：状态监控、问题排查、新建会话、发送消息、本机与 Tailscale 访问

## 1. 目标与布局

提供统一的中文管理控制台，复用现有 Codex Desktop、dsh 和 Telegram 桥接能力。
桌面采用侧边导航、会话列表、会话详情三栏布局；手机采用列表和详情分屏，输入框固定底部，新建会话为全屏表单。

```text
┌─────────────────────────────────────────────────────────────┐
│ Sea-Bridge       Codex ●   dsh ●   Telegram ●       设置 ⚙ │
├──────────┬─────────────────┬────────────────────────────────┤
│ 概览     │ 会话            │ 会话名称              来源标识 │
│ 会话     │ [+ 新建会话]    │ 项目 / 状态 / 更新时间         │
│ 消息记录 │ [搜索……]        ├────────────────────────────────┤
│ 设置     │ 来源：[全部 ▾]  │ 用户消息                       │
│          │                 │ 助手最终回复                   │
│          │ 会话列表        │ 提交状态 / 错误详情            │
│          │                 ├────────────────────────────────┤
│          │                 │ [输入消息……]          [发送]   │
└──────────┴─────────────────┴────────────────────────────────┘
```

概览展示来源连接状态、最近会话、最近桥接记录。会话支持来源筛选、标题搜索、历史查看、发送与新建。新建表单包含来源、项目、模型和首条消息。消息记录支持按来源、会话、状态和时间筛选。设置包含脱敏开关、脱敏配置展示、设备管理；首版不编辑密钥或其它运行配置。

## 2. 方案与取舍

选定管理控制台布局：监控和会话操作有独立入口，适合多来源桥接。聊天工作台更适合持续对话，但问题排查入口较弱；单页仪表盘初期简单，但记录与会话增长后拥挤。

由现有 Bun 进程提供静态网页及同源 API，使用现有 TypeScript、Bun SQLite 和浏览器原生能力，不新增依赖。业务数据定时刷新，设置同步与设备撤销采用 SSE。首版不实现逐字流式回复、终端模拟器、工具调用全文、网页审批、文件上传或会话删除。

## 3. 现有代码与接入边界

- `src/main.ts` 负责服务生命周期，新增 Web 服务随主进程启动和关闭。
- `CodexThreadStore` 提供现有未归档会话；`ThreadHistoryStore` 提供轮次状态和最终回复。必要的用户消息从现有 rollout 解析能力读取，仅接受已验证的消息结构。
- `CodexAppServerClient` 提供项目、模型及创建会话并启动首轮；`ProcessCodexQueueClient` 负责已有会话消息入队。
- `DshWebHostClient` 提供健康、项目、模型、会话、历史元数据、最终回复以及创建和提交接口。
- 现有 Telegram 路由和持久化使用 Telegram 消息或 update ID；网页不得伪造这些 ID 或复用其去重表。
- `src/security/redact.ts` 已有部分密钥过滤；需增加统一展示策略与正文过滤。
- 当前 logger 主要输出到控制台；增加有期限、有限量的结构化日志存储，历史未存储日志不能宣称可查询。

建议新增 `src/web/`：HTTP 路由、鉴权配对、来源适配、请求记录、展示过滤、设置事件以及静态资源分别负责单一职责。新增迁移放在独立模块，避免继续扩大 `StateDb` 的职责。只调整本功能需要的共享接口，不重构无关模块。

统一来源接口包含项目、模型、会话、历史、创建、发送和能力状态。每次操作明确使用来源与会话 ID；模型按单次请求传递，不临时修改 Telegram 默认模型。dsh 仍受现有读写功能开关控制。

## 4. 数据流与操作状态

读取：鉴权 → 来源或本地桥接记录 → 统一数据结构 → 当前全局展示策略 → 响应。
写入：鉴权及同源校验 → 输入验证 → 持久化请求认领 → 指定来源调用 → 更新结果 → 网页显示。

网页创建和发送使用随机请求 ID，服务端保存请求摘要、来源、目标、设备、状态和返回标识。同 ID 同内容返回已有结果；同 ID 不同内容拒绝。进入派发后发生超时、断线或进程重启，标为结果待确认，禁止自动重发。创建成功而首条消息未确认时保留已创建会话标识，避免重复创建。

显示状态区分提交中、已入队（Codex queue 成功）、已接受（来源确认提交）、明确失败、结果待确认。执行中和已完成必须来自已验证的轮次证据；无法确定时显示未知。dsh busy/writer-held 显示暂不可发送，不自动排队。来源不可用只影响对应来源。

会话及详情在前台每 3 秒刷新，后台暂停，回到前台立即刷新；同一查询不并发重叠。历史分页，保持输入草稿、阅读位置和稳定消息标识。无法读取的历史明确提示；仅有最终回复时按轮次展示，不伪造完整对话。网页自身提交的消息可用于补充展示，并以请求或来源消息标识去重。

## 5. 全局脱敏

默认开启，覆盖配置、会话标题、项目展示、消息正文、日志、错误信息及 SSE 内容。数据库保存开关和单调递增版本。所有已配对设备均可修改，更新须提交预期版本，冲突时提示刷新后操作。记录设备、时间与开关值审计，不记录敏感原文。

始终过滤已知配置密钥值、明确标注的密码、Token、Authorization/Cookie 及私钥内容。关闭脱敏也不返回这些内容。开启时额外遮盖可识别邮箱、手机号、IP 和本机路径；规则需集中实现并覆盖多行文本、嵌套对象和 URL。自动识别无法保证覆盖任意自然语言个人信息，界面用简短说明表达此边界。

展示策略不改写发给来源的任务内容，不改写上游会话历史，也不改变 Telegram 的现有展示行为。日志落盘前始终过滤密钥；普通路径等展示字段允许保留以支持关闭脱敏查询。已落盘被过滤的内容无法恢复。

每个响应带设置版本，动态响应设 `Cache-Control: no-store`。开关更新后 SSE 通知全部设备；客户端丢弃旧版本响应、清空已渲染数据并重新加载。事件流断开时隐藏敏感展示，重连先获取最新设置再恢复。后台或冻结标签页恢复时也须先同步。浏览器不将消息原文存到 localStorage、IndexedDB 或 Service Worker 缓存。已经看到、复制或截屏的内容无法撤回。

操作 ID 作为机器标识保持可寻址，界面显示可遮盖；脱敏不是隐藏协议中必须使用的会话标识的访问控制机制。

## 6. 本机与 Tailscale 访问、首次配对

Bun 服务仅监听 loopback。远程入口采用 Tailscale Serve 的 Tailnet 内 HTTPS 代理到该服务，不启用公网 Funnel，也不监听 `0.0.0.0`。实际主机的 Tailscale 可用状态、Serve 能力及入口地址在实施阶段验证；缺失时保留本机访问并明确报告远程未就绪。

本机及远程浏览器都需要配对。增加仅本机命令生成配对码：8 位数字、5 分钟有效、单次使用；新码使前一码失效。通过私有本机控制 socket 请求生成，配对码只向本机调用者显示，不写日志、不在书面规格或代码中写入真实秘密。

配对页不暴露状态、配置、会话或日志。服务端仅保存配对码和会话令牌的摘要，配对成功后设置 HttpOnly、SameSite=Strict Cookie；远程 HTTPS 使用 Secure，本机 HTTP 使用独立 host-only Cookie。设备会话绝对有效期 30 天，过期需重新配对。远程代理请求仅信任固定入口及受控代理，不信任客户端任意转发头。

配对接口限制请求体及频率：单来源每分钟最多 5 次失败，单配对码累计 10 次失败即失效；存在全局限速防止并发猜码。本机控制接口不经远程代理暴露。

写 API 校验精确 Origin/Host 白名单及 CSRF 凭证，无开放 CORS。设备页显示设备名称、配对时间、最近活动与当前设备，可撤销任意设备；撤销立即终止对应 SSE，后续 API 拒绝并退出登录。所有配对设备具有同等控制权限，首版不引入角色系统。

## 7. 持久化、日志与错误处理

新增独立表保存 Web 设置及版本、配对摘要、设备会话摘要、Web 操作与审计。保留 Telegram 与 dsh 现有表语义；仅做增量迁移。密钥不进入新增日志和操作摘要。为结果待确认的创建操作保存来源返回的会话 ID。

结构化日志默认保留 7 天，最多 10000 条；Web 操作和审计默认保留 30 天，最多各 10000 条，启动与运行时清理。分页读取，不扫描或暴露任意系统日志文件。详细消息优先按需读取来源，网页提交正文仅在展示需要时保存，执行同样的期限和密钥过滤；不保存用户输入中的真实密钥到新增正文存储。

API 使用稳定错误码及中文说明，页面提供明确的加载、空列表、来源离线、部分数据不可用和配对失效状态。未知提交结果提供刷新核查入口，不提供自动重试。拒绝直接展示未经处理的底层异常。网页内容以文本或安全 DOM 渲染，禁用来源消息中的原始 HTML。

## 8. 验证与验收

自动测试覆盖：配对有效期、单次使用、猜码限制、设备撤销、Cookie 与同源限制；来源隔离与禁用能力；请求去重与摘要冲突；超时和重启后的结果待确认；新建部分成功；模型按请求隔离；全局脱敏版本冲突、两设备同步、旧响应丢弃、断线恢复；密钥常驻过滤与正文规则；日志清理、分页和迁移；来源文本的脚本注入防护。

仓库现有命令为 `bun test`、`bun run typecheck` 和 `bun run build`。当前没有 lint/format 脚本，不擅自安装工具；实施前重新核对可用检查，运行相关测试与现有全套测试，分别报告结果。

实机验收覆盖本机、手机和第二台 Tailnet 电脑：首次配对、刷新保留登录、设备撤销、创建 Codex/dsh 会话并发送首轮、指定会话续发、真实最终回复与状态、断线与来源重启、双设备脱敏同步，以及 Telegram 原有链路回归。本次设计阶段未执行上述运行验收，不把源码存在视作运行能力已确认。
